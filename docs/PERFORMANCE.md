## 2. 结果总览

| 场景 | 分辨率 | DPR | 实际渲染像素 | 平均 FPS | p50 | p95 | 自适应后 DPR |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 桌面 1440×900 | 1440 × 900 | 1.0 | 1.30 MP | **222.0** | 4.2 ms | 8.3 ms | 1.0 |
| 桌面 1080p | 1920 × 1080 | 1.0 | 2.07 MP | **220.4** | 4.2 ms | 8.4 ms | 1.0 |
| 桌面 2× | 1280 × 800 | 2.0 | 4.10 MP | **233.0** | 4.2 ms | 4.3 ms | 2.0 |
| 移动 390×844 | 390 × 844 | 1.6 | 0.42 MP | **235.7** | 4.2 ms | 4.3 ms | 1.6 |
| 压力 1440p 2× | 2560 × 1440 | 2.0 | 14.75 MP | **65.3** | 12.5 ms | 45.9 ms | 2.0 |
| 压力 4K 2× | 3840 × 2160 | 2.0 | 33.18 MP | **5.1** | 87.5 ms | 750 ms | **1.5** |

### 结论

- **1080p / 1440p 单倍屏**：远高于 60 FPS，p95 低于 9 ms，性能余量充足。
- **1280×800 @ DPR 2**：4.1 MP，仍保持 233 FPS；高 DPI 桌面无需降级。
- **移动 390×844 @ DPR 1.6**：0.42 MP，235 FPS；手机端瓶颈更多在 GPU 带宽与发热，而非几何量。
- **1440p @ DPR 2（14.7 MP）**：65 FPS，仍可交互；p95 45.9 ms 说明复杂构图下有轻微抖动。
- **4K @ DPR 2（33 MP，等效 8K）**：属于极端压力场景，5 FPS；自适应在持续慢帧后把 DPR 从 2.0 降到 1.5，避免完全不可用。此场景不代表目标使用方式。

## 4. 帧预算与自适应策略

目标帧时间：**26.3 ms（38 FPS）** 作为“需要关注”的阈值。

```
每帧：
  updateScene(delta)        音频包络、出生动画、粒子、相机
  renderer.info.reset()
  composer.render()         Bloom + Grade + Output
  measurePerformance(rawDelta)
```

自适应逻辑：

1. 只累计 **< 400 ms** 的慢帧；着色器编译、分析、切标签造成的长停顿不计入。
2. 慢帧累计超过 **2.5 s**，且 DPR > 1.01 时，把 DPR 降低 **0.5**。
3. 只降低一次（`adaptiveReduced`），避免画质来回抖动。
4. `setDesign` / `setPhase` 时重置累计，避免生成阶段的长帧误触发。

4K 压力场景验证了这条链路：采样前 DPR 2.0 → 采样后 1.5。

## 7. 已知瓶颈

1. **4K + DPR 2**：33 MP 的 Bloom 链超出主流 GPU 的填充率预算；产品默认 DPR 上限 2，且自适应只降一次。若目标设备是 4K 笔记本，建议在控制室选择“均衡”。
2. **透明材质 overdraw**：流体有机的膜与水晶的玻璃在近距离叠层时最贵；已通过半分辨率 Bloom 与深度排序缓解。
3. **长时影像导出**：`MediaRecorder` 的编码队列在超长录制时可能滞后；32 秒 720p 实测约 49 秒，建议单段不超过 45 秒（代码已限制 `exportDuration = min(45, duration)`）。
4. **移动端发热**：持续 120 Hz 渲染会升温；可将质量切到“均衡”，DPR 会限制在 1.6。

## 8. 复现方式

```bash
npm run dev
# 另开终端
npm run test:perf
```

脚本会依次创建独立浏览器上下文，测量：
